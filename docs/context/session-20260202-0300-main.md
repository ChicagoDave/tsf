## Key Decisions

### 1. publishConfig Presence as Publish Signal
**Decision**: Use `publishConfig` object presence in package.json (rather than `private: false`) as the signal for whether a package should be processed by publish-conditioned targets.

**Rationale**:
- More explicit and intentional than inferring from absence of `private` field
- Aligns with npm's publish workflow (packages with publishConfig are intended for publication)
- Prevents accidental inclusion of packages that happen to not have `private: true`

### 2. Filter TSF-Internal Conditions from Exports
**Decision**: Remove TSF-internal conditions like `"publish"` from Node.js package.json exports conditions during sync.

**Rationale**:
- Node.js module resolution doesn't understand TSF-specific conditions
- Conditions in exports should only contain Node.js-recognized values (import, require, types, default, node, browser, etc.)
- TSF conditions are build-time configuration, not runtime resolution hints

### 3. Target Preference Order in Sync
**Decision**: Sort targets so publish-conditioned targets are evaluated first when determining `main`, `types`, and `exports` field values.

**Rationale**:
- For dual-target setups (local dev + npm publish), the published version should take precedence in package.json fields
- Ensures `npm publish` uses the correct output directory
- Local development still works via TypeScript project references and workspace resolution

## Architectural Notes

### Target Scoping Pattern
The `shouldSkipTarget()` function implements a critical architectural pattern for mixed monorepos:

```typescript
function shouldSkipTarget(pkg: PackageInfo, target: Target): boolean {
  if (target.condition === 'publish') {
    return !pkg.packageJson.publishConfig;
  }
  return false;
}
```

This simple predicate enables selective target application across 31 packages, processing 18 for npm target and 30-31 for local target. The pattern is consistently applied across build, sync, validate, and info commands.

### TSF-Internal vs. Runtime Conditions
TSF now maintains a clear separation between build-time configuration and runtime module resolution:
- **Build-time**: `condition: "publish"` in tsf.config.json controls which packages get which targets
- **Runtime**: Only standard Node.js conditions appear in package.json exports (import, require, types, default)

This prevents pollution of the npm package with build tool internals.

### Workspace Pattern Handling
Fixed a subtle bug in workspace pattern processing where negation patterns were being treated as additional include patterns. The corrected implementation:
1. Separate patterns into positive and negative lists
2. Use positive patterns for glob matching
3. Convert negative patterns to ignore patterns
4. Apply ignores during glob result filtering

This aligns with pnpm/yarn workspace semantics.
