### Critical Architecture Fix: Workspace Dependencies in Published Packages

**Problem Discovered**: The original TSF architecture correctly identified the need to rewrite `@scope/package` imports to relative paths for npm publish, but completely missed that `package.json` dependencies also contain `workspace:*` protocol references that npm cannot resolve. When consumers try to install published packages, npm fails at install time (before any code runs) with `EUNSUPPORTEDPROTOCOL`.

**Root Cause**: Import rewriting in JS/DTS files is necessary but not sufficient. npm reads dependencies from `package.json` at install time, and `workspace:*` is a pnpm-specific protocol that npm doesn't understand.

### Solution Architecture: Staging Directory with Clean Manifests

Implemented a dual-build system:

1. **Local build** (`tsf build` or `tsf build --local`): Unchanged behavior, compiles to `dist/` with workspace imports preserved for local development
2. **NPM build** (`tsf build --npm`): Compiles to staging directory outside workspace (`~/.tsf-publish/`, configurable via `TSF_PUBLISH_DIR`), generates clean package.json files with workspace deps stripped
3. **Publish** (`tsf publish`): Reads from staging dir, packs tarballs, publishes to npm

**Why staging directory**: The clean `package.json` files cannot coexist with source files in the workspace because pnpm would try to resolve them, and TypeScript would find duplicate `.d.ts` files during compilation. Staging directory solves both problems by being outside the workspace entirely.

### Rejected Approaches (Documented in docs/work/fix-it.md)

1. **Strip workspace deps from source package.json during sync** - Breaks local dev (pnpm needs workspace:* for symlinks)
2. **Temporarily modify package.json during publish, then restore** - Unacceptable UX (file mutations)
3. **Write publish output into package tree (dist-npm/)** - tsc finds .d.ts files there and breaks local dev
4. **Separate build step writing to workspace** - Same .d.ts collision problem
5. **Staging dir inside workspace (/npmpub/)** - pnpm finds package.json files and breaks
6. **Pack tarball directly from compiler output (no outDir)** - Compiler needs files on disk, cache needs persistent output

### Implementation Details

**Build Flow (`tsf build --npm`)**:
1. Compile to `~/.tsf-publish/<pkg-name>/`
2. Rewrite imports to relative paths
3. Transform declarations
4. Generate clean `package.json` (strip `workspace:*` deps, strip `devDependencies`, set entry points)
5. Copy README, LICENSE if present
6. Use incremental caching (separate cache keys from local builds)

**Publish Flow (`tsf publish`)**:
1. Read already-built packages from staging directory
2. Pack each into `.tgz` tarball via `npm pack`
3. Publish tarball via `npm publish <tarball>`
4. Support `--changed`, `--tag`, `--filter`, `--dry-run` flags

**Package JSON Transformation**:
- Strip all `workspace:*` dependencies
- Remove `devDependencies` entirely
- Preserve external dependencies (from npm registry)
- Set entry points (`main`, `types`, `module`, `exports`)
- Preserve `publishConfig`
- Never modify source `package.json`

## Key Decisions

### 1. Staging Directory Location: Native Filesystem

**Decision**: Use `~/.tsf-publish/` on native Linux filesystem (not `/mnt/c/` in WSL).

**Rationale**:
- Must be outside workspace to avoid pnpm/tsc conflicts
- WSL2 I/O performance is 10-100x faster on native Linux filesystem
- Configurable via `TSF_PUBLISH_DIR` for CI environments
- User home directory is standard temp location for build tools

### 2. Never Mutate Source Files

**Decision**: Source `package.json` is read-only. Clean manifests are generated files in staging dir.

**Rationale**:
- File mutations are bad UX (users hate tools that change their files)
- Git status becomes noisy
- Race conditions in parallel workflows
- Rollback complexity
- Breaking change to existing workflows

### 3. Separate Cache Keys for Local vs NPM Builds

**Decision**: `--npm` builds use separate cache keys from `--local` builds.

**Rationale**:
- Different output locations (staging vs dist/)
- Different import rewriting (relative vs workspace)
- Different package.json generation
- Must rebuild if switching modes

### 4. Publish Command Reads, Doesn't Build

**Decision**: `tsf publish` strictly handles npm operations. No compilation.

**Rationale**:
- Separation of concerns (build vs deploy)
- Users may want to inspect staging output before publish
- CI can cache staging directory between steps
- Explicit build step makes workflow clearer

## Architectural Notes

### The Manifest Generation Algorithm

`generatePublishManifest()` in `src/sync/package-json.ts` is the heart of the solution:

```typescript
export function generatePublishManifest(
  sourceManifest: PackageJson,
  target: BuildTarget
): PackageJson {
  const clean = {
    name: sourceManifest.name,
    version: sourceManifest.version,
    description: sourceManifest.description,
    // ... strip workspace:* from dependencies
    dependencies: stripWorkspaceDeps(sourceManifest.dependencies || {}),
    // ... set entry points from target config
    main: target.main || './index.js',
    types: target.types || './index.d.ts',
    // ... preserve publishConfig
  };
  return clean;
}
```

Key insight: We don't need to resolve workspace dependencies to npm versions. We can just strip them entirely because:
1. The compiled JS already has imports rewritten to relative paths
2. npm consumers will resolve relative imports at runtime
3. Workspace deps are dev-time concerns, not runtime concerns (for compiled output)

### Cache Invalidation Strategy

Separate cache keys prevent false cache hits:
- Local build: `${pkg.name}:${sourceHash}:local`
- NPM build: `${pkg.name}:${sourceHash}:npm:${targetHash}`

This means switching from `--local` to `--npm` triggers rebuild (correct behavior, since output format differs).

### Why Tarballs vs Direct Directory Publish

`npm publish` can accept either a directory or tarball. We use tarballs because:
1. Tarball is what npm actually uploads (directory gets packed internally anyway)
2. Tarballs can be cached/inspected before publish
3. `npm pack` gives us the exact bytes that will be published
4. Better visibility in `--dry-run` mode
