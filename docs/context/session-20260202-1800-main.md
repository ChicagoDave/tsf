## Key Decisions

### 1. Target-Aware Filtering via `--condition`
**Rationale**: Rather than adding a separate mechanism to filter packages during versioning, we reused the existing `shouldSkipTarget()` logic. This ensures versioning respects the same per-package and per-target skip conditions used during builds. A package with `"tsf": { "skip": true }` or target with `"condition": "publish"` when the package lacks `publishConfig` is automatically excluded.

**Implication**: Versioning is now consistent with build targeting — no disconnect between what gets built and what gets versioned.

### 2. Per-Subcommand Help System
**Rationale**: Moved from a monolithic help text to per-command help functions. This allows detailed examples for complex commands (build, version, validate) while keeping simple commands concise. Each help text explains flags, defaults, and usage patterns.

**Implication**: Users can now run `tsf version --help` instead of reading the README. This scales better as the CLI grows.

### 3. Version Bumping Logic
**Rationale**: Implemented semantic versioning bump logic that:
- Strips prerelease on `--bump patch` (1.0.1-beta → 1.0.1, not 1.0.2)
- Increments numeric suffix for same `--preid` (beta.1 → beta.2)
- Falls back to .0 when preid changes (alpha → beta.0)

**Implication**: Supports common release workflows: alpha → beta → rc → release, with intelligent prerelease management.

### 4. README Problem-First Positioning
**Rationale**: Lead with "the problem" instead of "what is tsf". Readers immediately understand whether tsf solves their pain (workspace imports at npm) vs. curiosity-driven exploration.

**Implication**: Higher engagement from qualified users; clearer mental model of the tool's scope.

## Architectural Notes

**Version Filtering Strategy**: The `--condition` flag leverages existing per-target `shouldSkipTarget()` checks. This creates a unified filtering model:
- Build targets: filtered by `skip` and per-package tsconfig overrides
- Version targets: same filters apply via `--condition`
- Future: Could extend to other operations (lint, test, deploy)

**Help System Scalability**: Moving from a single `printHelp()` to per-command functions enables:
- Rich examples per command
- Consistent formatting
- Easy to add new commands without breaking existing help
- Could be extracted to separate help.ts file if it grows further

**Integration Pattern**: The sharpee script model (dynamic publishConfig detection → tsf commands) is a template for other monorepo tooling. It shows how tsf can replace ad-hoc versioning and coordination scripts.
