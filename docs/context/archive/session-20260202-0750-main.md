### Integration Test Suite Debugging and Fixes

Starting from the previous session's staging directory implementation, this session focused on getting all tests passing. The initial test run revealed multiple root causes that were systematically identified and fixed.

### Root Cause #1: Missing `publishConfig` in Fixture Packages

**Problem**: The npm target was being silently skipped during `tsf build --npm` for fixture packages.

**Investigation**: `shouldSkipTarget()` in `/mnt/c/repotemp/tsf/src/orchestrator/index.ts:227-232` requires `publishConfig` to be present in package.json for any target with `condition: "publish"`. The fixture packages at:
- `/mnt/c/repotemp/tsf/tests/fixture/packages/core/package.json`
- `/mnt/c/repotemp/tsf/tests/fixture/packages/app/package.json`

lacked this field, causing the orchestrator to skip npm builds entirely.

**Fix**: Added `"publishConfig": { "access": "public" }` to both fixture package.json files.

**Learning**: The condition filtering logic assumes publish targets are intentional and require explicit opt-in via `publishConfig`. This is correct for real packages but was an implicit assumption that wasn't documented in test fixtures.

### Root Cause #2: Publish Targets in `generateFields()` Breaking Sync

**Problem**: After the staging directory refactor, `tsf sync` was generating package.json entry points pointing to `./dist-npm/index.js`, which no longer exists in the local workspace (npm output now goes to `~/.tsf-publish/`).

**Investigation**: `generateFields()` in `/mnt/c/repotemp/tsf/src/sync/package-json.ts:116-120` had logic to prefer publish-conditioned targets when generating entry points:

```typescript
const targets = pkg.targets.sort((a, b) => {
  if (a.condition === 'publish') return -1;
  if (b.condition === 'publish') return 1;
  return 0;
});
```

This was a vestigial pattern from when publish output lived in the package tree (`dist-npm/`). With the staging directory approach, publish targets write outside the workspace entirely.

**Fix**: Changed the sort to a filter that excludes publish-conditioned targets:

```typescript
const targets = pkg.targets.filter(t => t.condition !== 'publish');
```

**Rationale**: Package.json entry points must reference files in the local workspace. Publish targets write to staging (`~/.tsf-publish/`) which is invisible to the workspace. Only local/dev targets should contribute to package.json sync.

**Impact**: This ensures `tsf sync` only sets entry points from local builds (`dist/`), not staging builds. The staging directory's package.json has its own entry points set by `generatePublishManifest()`.

### Root Cause #3: Test File Parallelism Causing Race Conditions

**Problem**: Flaky test failures with missing build outputs and cache corruption.

**Investigation**: `tests/integration.test.ts` and `tests/integration-phase4.test.ts` both:
1. Run `beforeAll(() => cleanFixtureOutput())` which deletes all `dist/` directories
2. Run `beforeAll(() => pnpm build && tsf build)` which compiles fixtures
3. Run in parallel by default (vitest spawns multiple workers)

Timeline of race condition:
- Worker 1: `integration.test.ts` cleans fixture, builds
- Worker 2: `integration-phase4.test.ts` cleans fixture (deletes Worker 1's build output)
- Worker 1: Tests run, find missing dist/ files, fail
- Worker 2: Builds, tests pass

**Fix**: Set `fileParallelism: false` in `/mnt/c/repotemp/tsf/vitest.config.ts`:

```typescript
export default defineConfig({
  test: {
    fileParallelism: false,  // Integration tests share fixture state
    // ...
  }
});
```

**Rationale**: The fixture directory is shared state. Multiple test files modifying it concurrently causes non-deterministic failures. File-level serialization ensures cleanup → build → test happens atomically per file.

**Trade-off**: Test suite runs slower (serial instead of parallel), but correctness trumps speed for integration tests.

### Root Cause #4: Stale Cache Causing Build Skips

**Problem**: After one test file's cleanup, the next test file's build would skip compilation due to cache hits, even though outputs were deleted.

**Investigation**: `cleanFixtureOutput()` deleted `dist/` directories but not `.tsf-cache/`. The cache still contained entries like:

```
@testfixture/core:abc123hash:local -> VALID
```

When the next test file ran `tsf build`, the orchestrator would:
1. Read source files (unchanged)
2. Compute hash `abc123hash`
3. Check cache → hit
4. Skip compilation
5. Tests expect dist/ files → fail (they were cleaned!)

**Root Cause**: Cache invalidation was tied to source hash, not output existence. If someone manually deletes `dist/`, the cache doesn't know.

**Fix**: Added cache directory cleanup to `cleanFixtureOutput()` in both test files:

```typescript
function cleanFixtureOutput() {
  execSync('rm -rf tests/fixture/packages/*/dist tests/fixture/packages/*/.tsf-cache',
    { cwd: rootDir });
}
```

**Rationale**: Test fixtures should start from a completely clean state. Cache is a performance optimization; correctness requires ignoring it when explicitly cleaning.

**Future consideration**: TSF could add output existence checking to cache validation (cache hit valid only if output files still exist).

### Root Cause #5: Test Timeouts on WSL2

**Problem**: Integration tests were timing out at the default vitest timeout (5000ms).

**Investigation**: The integration test `beforeAll` hooks:
1. Run `pnpm build` (compiles TSF itself: ~10-15s on WSL2)
2. Run `tsf build` (compiles fixture packages: ~5-10s)
3. Run `tsf build --npm` (compiles to staging: ~5-10s)
4. Total: 20-35s, sometimes 60s+ due to WSL2 I/O latency

WSL2 filesystem performance on `/mnt/c/` (Windows NTFS mounted via 9P) is 10-100x slower than native Linux filesystem.

**Fix Applied**:

1. `/mnt/c/repotemp/tsf/vitest.config.ts`:
```typescript
export default defineConfig({
  test: {
    hookTimeout: 120000,    // 2 minutes for beforeAll/afterAll
    testTimeout: 30000,     // 30 seconds for individual tests
  }
});
```

2. `/mnt/c/repotemp/tsf/tests/integration.test.ts`:
```typescript
beforeAll(async () => {
  cleanFixtureOutput();
  execSync('pnpm build && tsf build', { cwd: rootDir });
}, 120000);  // Explicit 2-minute timeout
```

3. `/mnt/c/repotemp/tsf/tests/integration-phase4.test.ts`:
```typescript
test('detects missing files on publish attempt', async () => {
  // ... test body
}, 30000);  // Increased from default 5s
```

**Rationale**: WSL2 I/O latency makes these tests genuinely slow. The timeout increases are not hiding real performance problems; they're accommodating platform limitations. CI environments (native Linux) will run faster.

## Key Decisions

### 1. Exclude Publish Targets from Package.json Sync

**Decision**: `generateFields()` now filters out `condition: "publish"` targets entirely, rather than preferring them.

**Rationale**:
- Publish targets write to staging directory (`~/.tsf-publish/`) outside the workspace
- Package.json entry points must reference files in the workspace tree
- Only local/dev targets write to workspace (`dist/`)
- Staging directory has its own package.json (generated by `generatePublishManifest()`)
- Prevents broken references like `./dist-npm/index.js` when dist-npm/ doesn't exist locally

**Alternative considered**: Keep publish target in sync but remap output path. Rejected because staging directory is intentionally outside workspace; sync should only manage workspace files.

### 2. Serialize Integration Test Files

**Decision**: Set `fileParallelism: false` in vitest config.

**Rationale**:
- Integration tests share fixture directory state
- Cleanup/build/test must be atomic per file
- Race conditions cause flaky failures
- Performance cost (slower test runs) is acceptable for correctness
- Unit tests still run in parallel (no shared state)

**Trade-off**: Full test suite takes ~90-120s instead of ~30-40s. This is acceptable because:
- Integration tests are slow by nature (shell out to real builds)
- CI runs are infrequent (pre-commit, pre-push)
- Deterministic failures > fast flaky tests

### 3. Clean Cache in Test Fixtures

**Decision**: `cleanFixtureOutput()` now deletes `.tsf-cache/` in addition to `dist/`.

**Rationale**:
- Tests should start from known clean state
- Cache can mask bugs (false hits when outputs deleted)
- Incremental builds are user-facing feature; tests should verify fresh builds
- Cache correctness is tested separately in `cache.test.ts`

**Impact**: Integration tests always do full rebuilds (no cache hits). This is correct behavior for tests.

### 4. Increase Timeouts for WSL2

**Decision**: Set `hookTimeout: 120000` and `testTimeout: 30000` in vitest config.

**Rationale**:
- Integration tests shell out to real build processes
- WSL2 filesystem (Windows NTFS via 9P) has 10-100x I/O latency vs native Linux
- Tests are genuinely slow, not hanging
- Timeout increases accommodate platform, don't hide bugs
- CI (native Linux) will run faster with same timeout values

**Alternative considered**: Skip integration tests on WSL2. Rejected because WSL2 is a primary developer platform; tests must pass there.

## Architectural Notes

### The Staging Directory Invariant

This session revealed an important architectural invariant:

**Invariant**: Files in the workspace and files in the staging directory are in disjoint namespaces. They never share the same output location.

**Implications**:
1. Package.json sync (`tsf sync`) only manages workspace files
2. Publish manifest generation (`generatePublishManifest()`) only manages staging files
3. Entry points in workspace package.json point to `./dist/*`
4. Entry points in staging package.json point to `./*` (staging dir is publish root)
5. Import rewrites differ (workspace: preserve @scope/pkg, staging: rewrite to ../pkg)

This invariant prevents a whole class of bugs (duplicate files, conflicting entry points, tsc finding wrong .d.ts files).

### Cache Invalidation Lesson

This session exposed a cache invalidation edge case: what if someone manually deletes output files?

**Current behavior**: Cache remains valid (keyed on source hash), build skips, tests fail.

**Correct behavior (not yet implemented)**: Cache validation should check output existence:

```typescript
function isCacheValid(entry: CacheEntry, target: BuildTarget): boolean {
  if (!sourceFilesUnchanged(entry)) return false;
  if (!outputFilesExist(entry.outputs)) return false;  // NEW CHECK
  return true;
}
```

This is low priority (users rarely manually delete dist/) but should be documented as a known limitation.

### Test Isolation in Monorepos

Integration testing monorepo tools is tricky because:
1. Fixtures must be real packages (have package.json, node_modules, etc.)
2. Cleanup must remove build outputs but preserve source
3. Cache must be cleared to avoid cross-test pollution
4. Parallel test files race on shared fixture state

**Solution pattern**:
- Fixtures in `/tests/fixture/` (checked into git)
- `cleanFixtureOutput()` deletes generated files (dist/, .tsf-cache/)
- `beforeAll()` runs cleanup → build → cache warm
- `fileParallelism: false` serializes test files
- Individual tests can still run in parallel within a file (safe because they don't modify fixture)

This pattern should be documented for future test authors.
