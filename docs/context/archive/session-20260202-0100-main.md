## Key Decisions

### 1. Async Bundler API Required

**Problem**: esbuild's plugin system requires the async `build()` API, not `buildSync()`. Plugins use async `resolveId` and `load` hooks.

**Decision**: Made `buildPackageTarget` async and updated `runWithConcurrency` to handle `Promise<R>` return types. This allows seamless mixing of sync compilers (tsc) and async bundlers (esbuild, rollup).

**Rationale**: The plugin-based workspace resolution approach (see Decision 2) is cleaner and more maintainable than trying to pre-resolve imports before invoking the bundler. Async was the price of admission for plugins, but the change was localized and backward-compatible.

### 2. Workspace Resolution via Plugins

**Problem**: Bundlers need to resolve workspace package names (`@workspace/core`) to their source entry points so they can inline workspace code.

**Decision**: Implement custom plugins for both esbuild and Rollup that intercept bare specifier resolution and map workspace packages to source file paths.

**Alternatives considered**:
- Pre-transforming imports before bundling (rejected: breaks sourcemaps, increases complexity)
- Using bundler-specific path resolution config (rejected: inconsistent across bundlers)
- Relying on symlinks (rejected: doesn't work for source-to-source inlining)

**Rationale**: Plugins are the idiomatic way to extend bundler resolution in both esbuild and Rollup. The plugin approach is self-contained, preserves sourcemaps, and allows the bundler to do what it does best (dependency analysis, tree-shaking, code splitting).

### 3. No Declarations for Bundle Targets

**Problem**: Should bundled outputs include `.d.ts` files?

**Decision**: No. Bundle targets skip declaration emit entirely.

**Rationale**:
- Bundled output is typically consumed as a final artifact (CLI tool, browser bundle, Lambda function), not as a library
- The bundle itself doesn't preserve the original module structure, making `.d.ts` files meaningless
- Users who need declarations should use a separate target with `imports: "relative"` or `imports: "preserve"`
- This simplifies the bundler adapters and avoids the complexity of declaration bundling

### 4. Built-in TypeScript Support in Rollup Adapter

**Problem**: Rollup doesn't natively support TypeScript. The standard approach is to install `@rollup/plugin-typescript` or `@rollup/plugin-sucrase`.

**Decision**: Include a minimal built-in TypeScript transpilation plugin that uses esbuild for type stripping with `tsc.transpileModule()` as fallback.

**Rationale**:
- Reduces dependency footprint (no need for separate plugin package)
- Leverages esbuild for speed when available (most projects using TSF will have esbuild installed)
- Provides graceful fallback to TypeScript's built-in transpiler
- Keeps TSF self-contained and reduces configuration burden

**Trade-off**: This approach does type stripping only, not type checking. But that's consistent with TSF's philosophy (see architecture.md "Resolved Questions" section) - type checking is delegated to `tsc --noEmit`.

## Challenges Encountered

### Challenge: esbuild Plugin Async Requirement

**Issue**: Initial implementation used `esbuild.buildSync()`, which doesn't support plugins. Plugins are required for custom resolution.

**Resolution**: Switched to async `esbuild.build()` and propagated async through the call chain:
- Made `buildPackageTarget` async
- Updated `runWithConcurrency` to handle `Promise<R>`
- Added `await Promise.resolve(...)` wrapper to handle both sync and async functions

**Learning**: esbuild's plugin system is powerful but requires the async API. The buildSync limitation is documented but easy to miss.

### Challenge: Deep Import Resolution

**Issue**: Workspace packages can be imported as deep paths: `@workspace/core/utils/helper` in addition to `@workspace/core`.

**Resolution**: Plugin resolution logic checks for both exact matches and prefix matches with `/`:
```typescript
if (workspaceResolveMap.has(args.path)) {
  return { path: workspaceResolveMap.get(args.path)! };
}
for (const [name, entry] of workspaceResolveMap) {
  if (args.path.startsWith(name + '/')) {
    const subpath = args.path.slice(name.length + 1);
    const srcDir = path.dirname(entry);
    return { path: path.resolve(srcDir, subpath) };
  }
}
```

This ensures deep imports are resolved relative to the package's source directory.

### Challenge: Rollup External Logic

**Issue**: Rollup needs to know which imports to treat as external (Node builtins, third-party packages) vs. inline (workspace packages).

**Resolution**: Implemented comprehensive `external` function that checks:
1. Explicitly configured external packages
2. Node.js builtin modules (both `node:` prefixed and bare names)
3. Bare specifiers not in workspace map (assumed to be third-party)
4. Deep imports of workspace packages (not external)

The logic is more complex than esbuild because Rollup doesn't auto-externalize Node builtins.

## Architecture Notes

### Bundler vs. Compiler Distinction

TSF now has two execution paths for build targets:

**Compiler path** (`imports: "preserve"` or `imports: "relative"`):
1. Transpile TypeScript to JavaScript (tsc or esbuild)
2. Optionally emit declarations (tsc)
3. Transform imports in `.js` files (preserve workspace names or rewrite to relative)
4. Transform imports in `.d.ts` files

**Bundler path** (`imports: "bundle"`):
1. Bundle entry point with workspace resolution plugin
2. No import transformation (bundler resolves everything)
3. No declaration emit (bundles are runtime artifacts)

The bundler path is simpler because resolution happens during the bundle process via plugins, eliminating the need for post-processing.

### Workspace Resolution Strategy

Both bundlers use the same conceptual approach:

1. Build a map of workspace package names → source entry points
2. Register a resolution plugin with the bundler
3. When bundler encounters a bare import, check if it's a workspace package
4. If yes, resolve to source file path (allows inlining)
5. If no, mark as external (preserves third-party imports)

This strategy is bundler-agnostic and could be adapted for other bundlers (webpack, Parcel, etc.) in the future.

### Performance Characteristics

**esbuild bundler**:
- Extremely fast (Go-based, parallel)
- Limited tree-shaking (less aggressive than Rollup)
- Best for: Development builds, CLI tools, speed-critical workflows

**Rollup bundler**:
- Slower than esbuild (JavaScript-based)
- Superior tree-shaking (static analysis, scope hoisting)
- Best for: Production bundles, library distribution, size-critical scenarios

Users can choose via `bundler: "esbuild"` or `bundler: "rollup"` in target config.
