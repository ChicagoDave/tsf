## Key Decisions

### 1. Cache Key Composition
**Decision**: Include dependency cache keys in package cache key computation

**Rationale**: A package's output depends not just on its own source, but on the compiled output of its dependencies. By including dependency cache keys in the hash, we ensure that when a dependency changes, all dependents are correctly invalidated and rebuilt. This creates a cascade effect that maintains build correctness while maximizing cache hit rates.

### 2. esbuild Declaration Handling
**Decision**: Use separate `tsc --emitDeclarationOnly` pass for `.d.ts` files

**Rationale**: esbuild is extremely fast for transpilation but doesn't generate TypeScript declarations. Rather than forcing users to choose between speed and type safety, we run esbuild for `.js` output and tsc only for `.d.ts` files. This provides 80%+ of esbuild's speed benefit while maintaining full TypeScript type information for package consumers.

### 3. Parallel Build Safety
**Decision**: Only parallelize within dependency levels, never across them

**Rationale**: Packages in different dependency levels may depend on each other, so they must build sequentially (level 0, then level 1, etc.). However, packages within the same level are guaranteed to have no inter-dependencies, making them safe to build in parallel. This maximizes parallelism while maintaining correctness guarantees.

### 4. Watch Mode Cascade Strategy
**Decision**: Use reverse dependency map to rebuild dependents when source changes

**Rationale**: When a package's source changes, not only that package needs rebuilding—all packages that depend on it also need rebuilding to use the updated output. By maintaining a reverse dependency map, we can efficiently identify and rebuild the minimal set of affected packages, avoiding full monorepo rebuilds while ensuring correctness.

### 5. Lazy Loading esbuild
**Decision**: Import esbuild dynamically only when needed

**Rationale**: esbuild is an optional dependency—users may prefer tsc. By lazy-loading esbuild only when a target specifies `transpiler: "esbuild"`, we avoid forcing all users to install esbuild, reduce memory footprint, and provide clear error messaging when the dependency is missing.

## Architectural Notes

### Cache System Design
The cache implementation uses a content-addressed approach where the cache key is a SHA-256 hash of all inputs that affect build output. This ensures deterministic builds and automatic invalidation when any input changes. The cache is stored on disk per target/package, allowing fine-grained cache control.

### Compiler Abstraction Layer
The `src/compilers/` directory establishes a clean abstraction for transpilers. Each compiler adapter implements the same interface, making it easy to add additional transpilers (swc, Babel, etc.) in the future. The orchestrator depends only on the abstraction, not specific compiler implementations.

### Dependency-Aware Parallel Execution
The build orchestrator implements a sophisticated scheduling algorithm:
1. Topologically sort packages into dependency levels
2. Build each level sequentially (to respect dependencies)
3. Within each level, build packages in parallel (safe because no inter-dependencies)
4. Configurable concurrency limit prevents resource exhaustion

This provides optimal parallelism without compromising correctness.

### Watch Mode Architecture
The watcher uses a push-based model:
- File system events trigger rebuilds (not polling)
- Debouncing prevents rebuild storms during bulk edits
- Reverse dependency graph enables efficient cascade rebuilds
- Integrates with cache system to skip unchanged packages

This provides fast incremental rebuilds for large monorepos.
