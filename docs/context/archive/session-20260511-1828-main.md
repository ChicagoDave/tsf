# Session Summary: 2026-05-11 — main

## Status: Completed

## Goals

- Add a build-tool-level option that rewrites relative import specifiers in tsf's emitted JS to include the explicit file extensions Node ESM requires (`.js` for files, `/index.js` for directories).
- The need surfaced from a downstream consumer (Sharpee/Zifmia) hitting `Directory import not supported` when dynamic-importing a workspace package's `dist-esm/` build under Node 22+ strict ESM.
- Keep the fix orthogonal to the existing `imports: "relative"` strategy (which handles cross-package `@scope/pkg` rewriting) — this is a separate concern about intra-package relative paths.

## Completed

### 1. New `esmExtensions` target option

Added `esmExtensions?: boolean` to `TargetConfig` in `src/types.ts` with doc explaining:

- the rewrite contract (`./foo` → `./foo.js` if file exists; `./foo` → `./foo/index.js` if directory exists with `index.js`)
- idempotency on already-extensioned and unresolvable specifiers
- the bare-specifier carve-out (those go through the `imports` strategy, not this pass)
- why this is needed: strict Node ESM in Node 22+ refuses directory and extensionless relative imports

Default is `false`. Consumers opt in per-target.

### 2. New `transformEsmExtensions` function

Added to `src/transform/imports.ts` alongside the existing `transformImports`:

- Scans every `.js` file under `target.config.outDir`
- Rewrites three patterns: `import/export ... from "..."` (static), `import "..."` (side-effect), `import("...")` (dynamic)
- Only operates on relative specifiers (`./` or `../`); bare specifiers (`@scope/pkg`, `lodash`, `node:fs`) are passed through unchanged
- Already-extensioned specifiers (`.js`, `.mjs`, `.cjs`, `.json`) are left alone — pass is idempotent
- Unresolvable specifiers (neither `./foo.js` nor `./foo/index.js` exist on disk) are left alone too — conservative; preserves diagnostic value of broken imports rather than swallowing them
- Re-exports the function from `src/index.ts`
- Orchestrator calls it right after `transformImports` and before `transformDeclarations` (`src/orchestrator/index.ts`)

### 3. Regex tightening — multi-line `export from`

The existing `ESM_FROM_RE` used `.*?` which does not match across newlines by default. Multi-line forms like:

```js
export {
  A,
  B,
} from './source';
```

were silently skipped. Caught during the integration verification against `@sharpee/stdlib`'s `dist-esm/channels/index.js`, which uses exactly this pattern. Added the `s` (dotall) flag so `.` crosses newlines. The fix benefits the existing `transformImports` rewriter too — same regex, same multi-line bug.

### 4. Added `ESM_DYNAMIC_RE`

New regex captures `import("./x")` style dynamic imports. Static imports were handled by the existing `ESM_FROM_RE`; dynamic imports needed their own pattern because the syntax is a function call rather than a `from` clause.

### 5. Test suite — 15 new tests

`tests/esm-extensions.test.ts` exercises:

- file-target rewrites (`./foo` → `./foo.js`)
- directory-target rewrites (`./foo` → `./foo/index.js`)
- trailing-slash preservation (`./foo/` → `./foo/index.js` without double slash)
- multi-line `export { ... } from '...'`
- mixed `import from` + `export from` in one file
- side-effect `import './x'`
- dynamic `import("./x")`
- no-op on already-extensioned `.js` / `.json`
- no-op on bare specifiers (`lodash`, `@scope/pkg`, `node:fs`)
- no-op on unresolvable relative specifiers
- idempotency (second run on the same file changes nothing)
- gate respect (`esmExtensions: false` is a complete no-op)
- graceful handling of missing `outDir`

All tests build minimal `outDir` trees in tempdirs and exercise the transformer directly — no CLI or orchestrator involvement, isolated unit-test scope.

Full suite: **108/108 tests pass** (up from 94 — 14 new tests, then +1 for the multi-line case). Build clean (`pnpm build`).

## Key Decisions

### `esmExtensions` is its own field, not a new `imports` value

The existing `imports` enum is about workspace-package strategy (preserve / relative / bundle / specifier-map). The new behavior is orthogonal — intra-package relative paths — and applies whether `imports` is `preserve` or `relative`. Keeping it a separate boolean avoids overloading `imports` semantics and lets consumers enable the extension-append independently of how they handle workspace packages.

### Conservative on unresolvable specifiers

The rewriter resolves each specifier against the importing file's directory and only rewrites if the target file/directory exists. Unresolvable specifiers are left alone rather than guessed at. Reasoning: if a downstream tool needs a non-existent path resolved differently (e.g., a synthetic module added by another plugin), that's the tool's call to make. A best-effort rewrite that mangles unfamiliar paths would break opaque setups silently.

### Reuse existing rewrite-call ordering

The orchestrator already runs `transformImports` then `transformDeclarations`. The new `transformEsmExtensions` slots between them. Order matters: `transformImports` (when `imports: "relative"`) emits paths like `../pkg/dist/index.js` that already have `.js`. The new pass is idempotent on those, so running it second is safe. Running it first would not change anything because the rewritten cross-package paths come out already extensioned.

## Notes

- The `MODULE_TYPELESS_PACKAGE_JSON` warning Node 22+ emits when loading the rewritten `dist-esm/` files is independent of this fix — it asks consumers to add `"type": "module"` to the package.json or rename outputs to `.mjs`. The current Sharpee packages emit dual CJS/ESM with `exports` conditions, which is the correct dual-publish pattern; the warning is informational, not an error.
- tsx's loader was observed to bypass the freshly-rebuilt `dist-esm/` even after the fix landed — appears to cache resolved package paths aggressively. Sharpee's downstream perf harness switched to `tsc + node` to sidestep this. Worth noting if other tsf consumers run their harnesses under tsx and don't see the fix take effect — try plain `node` first.
- No behavior change for existing tsf consumers — `esmExtensions` defaults to `false`. Existing builds are byte-identical.
