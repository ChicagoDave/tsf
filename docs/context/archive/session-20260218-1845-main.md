### Cross-Platform esbuild Loader

**Problem**: When `pnpm install` runs under WSL, only `@esbuild/linux-x64` is downloaded. If tsf is then invoked from Windows (e.g. PowerShell), esbuild's JS module loads fine but throws at build time because the native binary is for the wrong platform. This blocked the Sharpee project's `build-release.ps1` script from running on Windows.

**Solution**: Created a shared esbuild loader with automatic platform binary installation.

**New file**: `src/utils/esbuild-loader.ts`
- Loads esbuild JS module via `require('esbuild')`
- Runs a probe build (`buildSync` with empty input) to verify the native binary works
- If probe fails with a platform mismatch error, auto-installs the correct binary: `npm install --no-save @esbuild/{platform}-{arch}`
- Clears Node's require cache and retries
- Caches the verified module for subsequent calls (no re-install)
- Handles all platform combinations: win32-x64, win32-arm64, darwin-x64, darwin-arm64, linux-x64, linux-arm64

**Updated files**:
- `src/compilers/esbuild.ts` - Removed inline `loadEsbuild()`, now imports from shared loader
- `src/compilers/esbuild-bundler.ts` - Same change

**Testing**: Verified on Windows with only `@esbuild/linux-x64` installed:
1. First call: detected wrong binary, installed `@esbuild/win32-x64`, built successfully
2. Second call: loaded instantly from cache, no re-install

## Key Decisions
- Used `npm install --no-save` to avoid modifying the project's package.json
- Probe approach (build empty input) rather than checking at require time, because esbuild's JS module loads successfully regardless of platform - the error only surfaces during actual builds
- Clearing all esbuild-related require cache entries (not just the main module) to ensure the platform binary resolution picks up the new package

## Context
This work was driven by the Sharpee project's need for a Windows-native Zifmia release build script (`packages/zifmia/build-release.ps1`). The Sharpee dev environment uses WSL for daily builds, but the Tauri desktop app build requires running from native Windows/PowerShell. The esbuild platform mismatch was the blocking issue.
