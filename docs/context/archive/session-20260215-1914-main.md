### Critical Bug Fix: Workspace Dependencies in Published Packages

**Context**: Packages published via ts-forge's npm publishing workflow were unusable by consumers. Two distinct bugs were causing this failure.

#### Bug 1: Import Rewriting Broke Package Specifiers

**Location**: `src/orchestrator/index.ts`, line 166

**Problem**:
- In npm build mode, the orchestrator was forcing `imports: 'relative'`
- This triggered import rewriting via `transform/imports.ts`
- All workspace package imports like `require("@sharpee/core")` were rewritten to broken relative paths like `require("./src/index.js")`
- Since each package is published independently to npm, relative paths between packages don't work

**Fix**: Changed npm mode to use `imports: 'preserve'` instead. This keeps package specifiers as-is (e.g., `require("@sharpee/core")` stays as `require("@sharpee/core")`). Consumers will install workspace packages as regular npm dependencies.

#### Bug 2: Workspace Dependencies Deleted Instead of Resolved

**Location**: `src/sync/package-json.ts`

**Problem**:
- `generatePublishManifest()` called `stripWorkspaceDeps()` which completely deleted all `workspace:*` dependencies
- Published packages had no dependencies on their workspace siblings
- Example: `@sharpee/sharpee` was published with only `fflate` as a dependency, missing all 17 `@sharpee/*` packages it actually requires

**Fix**:
- Added new `resolveWorkspaceDeps()` function that converts pnpm workspace protocol to real version numbers
- Examples: `workspace:*` → `^0.9.87`, `workspace:^` → `^0.9.87`, `workspace:~1.0.0` → `~1.0.0`
- Updated `generatePublishManifest()` to accept optional `packages: Map<string, PackageInfo>` parameter for version lookup
- Falls back to reading version from package.json on disk if `PackageInfo.version` isn't set
- Marked `stripWorkspaceDeps()` as `@deprecated` (preserved for backward compatibility)

## Key Decisions

### 1. Preserve Package Specifiers in NPM Mode
Changed import strategy from `'relative'` to `'preserve'` for npm builds. This aligns with how npm packages are meant to work: each package declares dependencies in package.json, and consumers install them separately.

**Rationale**: The monorepo workspace can use relative paths internally, but published packages must reference each other via npm package names.

### 2. Resolve Workspace Protocol to Versions
Created `resolveWorkspaceDeps()` to convert pnpm's `workspace:*` protocol to actual version numbers rather than deleting dependencies.

**Rationale**: Consumers don't use pnpm workspaces, so workspace protocol must be resolved to standard semver ranges before publishing.

### 3. Make Version Lookup Optional
Added `packages` parameter to `generatePublishManifest()` rather than making it required.

**Rationale**: Allows for fallback to disk-based version lookup if the packages map isn't available, maintaining backward compatibility.

## Architectural Notes

### Workspace Protocol Handling
The new `resolveWorkspaceDeps()` function handles all pnpm workspace protocol variants:
- `workspace:*` → uses package's current version with `^` range
- `workspace:^` → uses package's current version with `^` range
- `workspace:~` → uses package's current version with `~` range
- `workspace:1.2.3` → uses explicit version as-is

This ensures published packages have proper semver dependencies on workspace siblings.

### Import Strategy Split
- **Workspace builds**: Can use any import strategy (relative, preserve, etc.)
- **NPM builds**: Must use `preserve` to maintain package specifiers
- **Transform step**: Import rewriting is skipped when strategy is 'preserve'
