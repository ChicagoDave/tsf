### Critical Bug Fix: rootDir Widening Logic

**File:** `src/compilers/tsc.ts`

**Problem Identified:**
The rootDir widening mechanism only triggered when ts-forge injected NEW workspace paths (controlled by `needsBaseUrl` flag). However, when a user's tsconfig already contained paths pointing outside rootDir (e.g., `@test/core: ["../core/src/index.ts"]` with `rootDir: "src"`), the widening was completely skipped, causing TypeScript TS6059 errors.

**Solution Implemented:**
- Replaced the `needsBaseUrl`-based check with a comprehensive scan of ALL path entries (both user-provided and ts-forge-injected)
- If any path resolves outside the package's effective rootDir, rootDir is automatically widened to the workspace root
- This ensures compatibility with both user-managed and tool-managed path configurations

**Impact:** Unblocks multi-package workspace builds where packages reference each other via workspace protocol

### Output Flattening for Widened rootDir

**Files:** `src/compilers/tsc.ts`, `src/transform/imports.ts`, `src/transform/declarations.ts`

**Problem Identified:**
When rootDir is widened to workspace root, TypeScript outputs a nested directory structure mirroring the full workspace tree. For example:
- Expected: `dist-npm/index.js`
- Actual: `dist-npm/packages/app/src/index.js`

Additionally, dependency source files were being duplicated into the output directory.

**Solution Implemented:**

1. **Post-compilation flattening** (`src/compilers/tsc.ts`):
   - Added `flattenWidenedOutput()` function that moves the package's own files from nested paths back to outDir root
   - Removes extraneous directory structures
   - Cleans up dependency source duplicates

2. **Output path computation** (`src/transform/imports.ts`, `src/transform/declarations.ts`):
   - Added `getOutputEntryPoint()` helper that strips the rootDir prefix when computing dependency output file paths
   - Example: `src/index.ts` with `rootDir=src` produces `index.js` not `src/index.js`
   - Reads dependency's tsconfig to determine correct rootDir for accurate path stripping

**Impact:** Ensures clean, flat output directory structure matching user expectations regardless of rootDir widening

## Key Decisions

### 1. Universal rootDir Widening Check

**Decision:** Check ALL path entries (user + injected) rather than only newly-injected paths.

**Rationale:**
- More robust and predictable behavior
- Handles user-configured workspace references correctly
- Prevents subtle configuration-dependent failures
- Aligns with principle of least surprise

### 2. Post-Compilation Flattening Approach

**Decision:** Flatten output directory structure after TypeScript compilation rather than adjusting outDir computation beforehand.

**Rationale:**
- Simpler implementation (fewer edge cases)
- More maintainable (clear separation of concerns)
- Robust against TypeScript version changes
- Easier to debug (output structure is predictable before flattening)

### 3. Dependency rootDir Resolution

**Decision:** `getOutputEntryPoint()` reads each dependency's tsconfig to determine its rootDir.

**Rationale:**
- Accurate output path computation for dependencies with varying configurations
- Respects per-package tsconfig settings
- Prevents hardcoded assumptions about project structure
- Enables correct relative path calculation for import/declaration rewriting

## Architectural Notes

### Import Resolution Strategy

The transform pipeline now correctly handles the full matrix of:
- **Targets**: `local` (development) vs `npm` (publish)
- **Module formats**: ESM vs CJS (future)
- **Import styles**: workspace protocol vs relative paths

The critical insight is that output path computation must respect each package's individual rootDir configuration. A workspace-level assumption breaks down in heterogeneous monorepos.

### Testing Philosophy

The test suite follows a two-tier approach:
1. **Unit tests**: Focus on core algorithms (dependency ordering, circular detection)
2. **Integration tests**: Verify end-to-end compilation across realistic workspace fixtures

This provides both confidence in low-level correctness and validation of real-world workflows.

### TypeScript Compiler Integration

Working with TypeScript programmatically requires careful handling of:
- Path mapping edge cases (absolute vs relative, glob patterns)
- rootDir inference vs explicit configuration
- Output directory structure with varying rootDir settings
- Declaration emit in multi-package scenarios

The flattening approach acknowledges that post-processing is often simpler than pre-configuration when dealing with complex compiler behavior.
