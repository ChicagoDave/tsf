## Key Decisions

### 1. Detection-First Init Strategy

**Decision:** Enhanced `tsf init` attempts to infer configuration from existing project structure before falling back to templates.

**Rationale:**
- Reduces friction for existing projects migrating to ts-forge
- Leverages existing package.json and tsconfig.json as source of truth
- Preserves developer intent from existing configuration
- Template fallback ensures new projects still get sensible defaults

**Implementation details:**
- Detection runs in phases: package.json → tsconfig.json → workspace topology
- Each phase can fail gracefully and fall back to the next
- Detected configuration is merged with defaults, not replaced

### 2. Idempotent Configuration Management

**Decision:** Re-running `tsf init` merges new targets rather than overwriting existing configuration.

**Rationale:**
- Safe to run multiple times as project evolves
- Allows iterative refinement of build configuration
- Prevents accidental loss of manual customizations
- Supports workflow where developers start with defaults and gradually tune

**Trade-offs:**
- More complex implementation (need merge logic)
- Requires clear documentation about merge behavior
- No "reset to defaults" path without manual deletion

### 3. Conservative Sync Scope

**Decision:** `tsf sync` only generates fields directly derivable from target configurations. It doesn't modify or remove unrelated package.json fields.

**Rationale:**
- Minimizes risk of unintended side effects
- Preserves fields managed by other tools (dependencies, scripts, etc.)
- Makes sync behavior predictable and auditable
- Supports hybrid workflows where some fields are hand-maintained

**Fields generated:**
- `main`, `module`, `types` - for single-format compatibility
- `exports` - for dual-format and subpath exports
- `bin` - for CLI executables
- `publishConfig` - for publish-specific overrides

**Fields preserved:**
- Everything else (dependencies, scripts, repository, keywords, etc.)

### 4. Comprehensive Validation Strategy

**Decision:** Validation checks both package.json accuracy (do declared entry points exist?) and output quality (declarations, import resolution).

**Rationale:**
- Package.json correctness is necessary but not sufficient
- Import rewriting bugs would only manifest at runtime without validation
- Declaration parity ensures TypeScript consumers get proper types
- Early detection prevents publish mistakes

**Validation categories:**
- **Structural** - Files exist on disk
- **Consistency** - Declarations match JavaScript output
- **Resolution** - Imports are properly resolved for target mode
- **Completeness** - All exports are reachable

### 5. Package Manager Auto-Detection for CI

**Decision:** GitHub Action workflow generation detects package manager and configures setup accordingly.

**Rationale:**
- Different package managers require different caching strategies
- Lock file location varies (pnpm-lock.yaml, yarn.lock, package-lock.json)
- Setup actions differ (pnpm/action-setup, setup-node with cache)
- Auto-detection eliminates manual configuration errors

**Detection order:**
1. Check for `pnpm-workspace.yaml` → use pnpm
2. Check for `yarn.lock` → use yarn
3. Fall back to npm

## Architectural Notes

### Layered CLI Architecture

The enhanced CLI demonstrates a clear separation of concerns:

```
CLI Layer (src/cli/)
  ├─ index.ts      - Argument parsing, command dispatch
  ├─ detect.ts     - Project introspection (stateless utilities)
  ├─ init.ts       - Config generation (uses detect + orchestrator)
  └─ gh-action.ts  - Workflow generation (uses detect)

Build Context Layer (src/orchestrator/)
  └─ loadBuildContextPublic() - Exposes build graph for CLI commands

Domain Logic Layer (src/sync/, src/validate/)
  ├─ sync/package-json.ts - Field generation from targets
  └─ validate/index.ts    - Output verification against targets
```

This structure allows:
- CLI commands to share detection logic without coupling
- Domain logic (sync, validate) to operate on build context without CLI concerns
- Testing of detection, generation, and validation independently

### Detection as Composition

The detection system composes multiple strategies:

```typescript
// Pseudo-code architecture
function detectTargets(pkg: PackageJson, tsconfig: TSConfig, workspace: Workspace): Target[] {
  return [
    ...detectFromExports(pkg),
    ...detectFromBin(pkg),
    ...detectFromLegacyFields(pkg),
    ...detectFromTSConfig(tsconfig)
  ].filter(deduplicateTargets);
}
```

Each detector is independent and can fail without breaking others. This makes the system:
- Resilient to missing or malformed configs
- Easy to extend with new detection strategies
- Testable at the detector level

### Validation as Pre-Flight Check

Validation is designed to run after build but before publish:

```
Development cycle:
  tsf build → (optional) tsf validate → manual testing

CI pipeline:
  tsf check → tsf build --all → tsf validate → publish

Pre-publish:
  tsf build --all --sync-package-json → tsf validate → npm publish
```

This catches:
- Missing files that would cause import errors
- Declaration/JS mismatches that break TypeScript consumers
- Workspace specifier leaks that fail in npm
- Invalid exports that break Node.js resolution

### Smart Target Detection

The detection system successfully infers targets from diverse project structures:

```javascript
// Example 1: Modern ESM library with exports
{
  "exports": {
    ".": {
      "import": "./dist/index.mjs",
      "require": "./dist/index.js"
    }
  }
}
// → Detects: esm target + cjs target

// Example 2: CLI tool

// → Detects: node-cjs target + outFile

// Example 3: Legacy single-format
{
  "main": "./dist/index.js",
  "types": "./dist/index.d.ts"
}
// → Detects: cjs target with declarations
```

### Robust Package.json Merging

The sync implementation preserves developer intent:

```javascript
// Original package.json
{
  "name": "my-package",
  "version": "1.0.0",
  "scripts": { "test": "jest" },
  "dependencies": { "react": "^18.0.0" }
}

// After tsf sync (with esm+cjs targets)
{
  "name": "my-package",
  "version": "1.0.0",
  "scripts": { "test": "jest" },       // Preserved
  "dependencies": { "react": "^18.0.0" }, // Preserved
  "main": "./dist/index.js",            // Generated
  "module": "./dist/index.mjs",         // Generated
  "types": "./dist/index.d.ts",         // Generated
  "exports": {                          // Generated
    ".": {
      "types": "./dist/index.d.ts",
      "import": "./dist/index.mjs",
      "require": "./dist/index.js"
    }
  }
}
```
