# TypeScript 6.0 compatibility — Phase 1 findings

**Recorded**: 2026-11-03, session 9ca055, TypeScript 6.0.3 installed (`npx tsc --version` → 6.0.3; was 5.9.3 under `^5.7.0`).
**Baseline before install**: `pnpm build` green, `pnpm exec vitest run` 12 files / 152 tests green, `npx tsc --noEmit` exit 0.

Provenance: every row marked [verified] was reproduced by running 6.0.3 in this repo. Rows marked [reported] come from the TypeScript 6.0 release notes (typescriptlang.org, fetched 2026-11-03) and were not exercised here.

## 2. Default changes and what they touch in TSF

| # | 6.0 change | Effect on TSF or its users | Call | Phase |
|---|---|---|---|---|
| D1 | `module` defaults to `esnext` regardless of target [reported; 5.x behavior verified: with `target: ES2022` and no `module`, 5.9.3 already emits ES modules, since 5.x defaulted to `es2015` for ES2015+ targets and to `commonjs` only for ES3/ES5] | A user tsconfig without `module` and a target without `module` emits whatever the compiler's default is; the CJS-to-ESM flip on upgrade affects only ES3/ES5-target users, but the format is decided by the compiler version either way. TSF passes `parsedConfig.options` through, so the change is silent. `resolveModuleKind()` (`src/compilers/tsc.ts:~250`) also lacks `preserve`. | **Done in Phase 3**: `compile()` logs a `logger.warn` naming the target as the place to set `module` when neither side sets it; the format is deliberately NOT pinned (the target is where format is decided). `preserve` added to `resolveModuleKind()`. Tested in `tests/ts6-compat.test.ts` (D1 cases, version-conditional format assertion). | 3 (done) |
| D2 | `types` defaults to `[]` (was all `@types/*`) [reported] | TSF's own build passed because every file imports `fs`/`path`, which pulls `@types/node` in by import. User packages relying on ambient `@types/*` globals break on 6.0; TSF's `getPreEmitDiagnostics` surfaces that as ordinary errors, not a TSF defect. | **Done in Phase 3**: `"types": ["node"]` in `tsconfig.json`. User documentation in Phase 4's README note. | 3 (done) |
| D3 | Default `rootDir` is the tsconfig directory (was longest common path) [reported] | `getOutputEntryPoint()` (three copies: `src/compilers/tsc.ts:441`, `src/transform/imports.ts:240`, `src/transform/declarations.ts:193`) falls back to `'src'` when the tsconfig has no `rootDir`. Wrong on both 5.x and 6.0 and now wrong in a new way. TSF's own tsconfig sets `rootDir` explicitly, so TSF itself is unaffected. | **Done in Phase 3**: new `src/utils/tsconfig.ts` `resolveRootDir()` returns the declared `rootDir`, else the common source directory (5.x's inference), else the tsconfig dir. The tsc adapter and the esbuild declaration emit pin `rootDir` to it when the user omits it, so 6.0 emits the same layout as 5.x; all three `getOutputEntryPoint()` copies read their fallback from it (copies NOT consolidated, issue 3). **Decision worth an ADR**: TSF pins rootDir to the common source directory rather than adopting 6.0's tsconfig-dir default; recorded as ADR-0003 (`docs/adrs/0003-pin-rootdir-to-common-source-directory.md`, confirmed 2026-11-04; issue 8 closed). | 3 (done) |
| D4 | `strict` defaults to `true` [reported] | TSF already `strict: true`. Users without `strict` see new type errors through TSF; not a TSF defect. | None. Document. | — |
| D5 | `esModuleInterop` / `allowSyntheticDefaultImports` can no longer be `false` [reported] | TSF sets `esModuleInterop: true`. Fixture sets it true. | None. | — |
| D6 | `target` defaults to current-year ES [reported] | TSF and fixture set `target` explicitly. | None. | — |
| D7 | `moduleResolution: classic`, `module: amd/umd/systemjs/none`, `outFile` removed [reported] | `resolveModuleKind()` never mapped these; `TargetConfig.outFile` exists for bundlers only, not passed to tsc. | None. | — |
| D8 | Compiler API "continues to be API compatible with 5.9" [reported] | `createProgram`, `emit`, `getPreEmitDiagnostics`, `readConfigFile`, `parseJsonConfigFileContent`, `transpileModule`, `ts.sys` all still present; TSF's build and 130 non-integration tests pass unchanged. [verified: no API-level failure anywhere] | None for 6.0. TS 7 removes all of these; out of scope. | — |
| D9 | `module` override over `nodenext` resolution [verified by reasoning from TS5110; not a 6.0 change] | A target that overrides `module: commonjs` while the user tsconfig has `moduleResolution: nodenext` yields TS5110 (`module` must be NodeNext when resolution is NodeNext) on both 5.x and 6.0. TSF's recommended 6.0-clean user config for CJS output is therefore `bundler` resolution (6.0 accepts bundler + commonjs; on 5.x TSF downgrades to node10), or `nodenext` for both fields with no target `module` override. ## 4. ignoreDeprecations decision

`"ignoreDeprecations": "6.0"` was in `tsconfig.json` (Phase 1-2) and the fixture tsconfigs (Phase 1) so the suite could run; **removed in Phase 2 (fixture) and Phase 3 (TSF), none remain**. It is never to be injected into user builds: a user who wants it sets it in their own tsconfig, and TSF already passes it through via `parsedConfig.options`.
